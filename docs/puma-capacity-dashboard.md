# Puma capacity dashboard

`Puma-frontend-<environment>` helps operators see queued requests, spare web
request threads and gaps in monitoring. It reads the optional `TradeTariff/Puma`
metrics and existing application logs; creating the dashboard does not enable
collection or change application configuration, ECS tasks or permissions.

## Start here

Each service summary uses the same order:

1. **Queued requests: busiest worker** — maximum internal Puma queue depth.
2. **Available threads: least spare worker** — minimum available thread slots.
3. **Reporting collectors: seen per minute** — collectors with a log sample.
4. **Running and desired ECS tasks** — compare with reporting collectors.

The dashboard links to backend UK/XI capacity and this guide. Worker diagnostics
sit below the summary. Thread totals and queue totals have separate charts and
explicit scope/units. There is no separate shared dashboard resource.

**Missing telemetry is not zero or spare capacity.** Collector counts are a
coverage proxy, not an exact concurrent task count: restarts and rolling
replacements can contribute multiple identities in one minute. A collector may
also report stale or unready workers. Check reporting/expected/stale/unready
worker coverage in the diagnostics before trusting spare capacity.

An empty internal queue does not prove service health. These queues exclude
socket/network waits and Sidekiq. Frontend and backend capacity are separate:
a slow backend may occupy frontend threads while backend requests still queue.
Extrema may come from different workers and times, not the same bottleneck.
Do not introduce health thresholds until a baseline has been agreed.

## Sampling and interpretation

Summary metrics and reporting-collector bins use 60 seconds. Diagnostic log
queries take one latest snapshot per collector per 10-second bucket, then sum
across collectors. **Never sum repeated gauge observations over time.** Totals
cover reporting workers only, not exact instantaneous service capacity. Records
without worker capacity are excluded rather than aggregated into a false zero.
Sampling boundaries, task turnover and missing reports can distort the result.

Use short windows for diagnostic Logs Insights queries; each query incurs scan
cost. Logs must preserve the raw `event = "puma.metrics"` JSON, with the correct
`Environment` and `Service` properties. Metrics must use those same dimensions.
The dashboard definition alone does not create metric series or prove extraction.

High-resolution CloudWatch detail is retained for 3 hours; 1-minute data for
15 days, 5-minute data for 63 days and 1-hour data for 455 days. Longer windows
need coarser log bins and explicit treatment of collector turnover. Historical
sub-minute shape cannot be reconstructed from aggregated metrics.

## Rollout checks

Use the normal approved workflow, initially outside production. Collection is
opt-in and must remain disabled until separately enabled in application
configuration. No production load test is authorised by this dashboard change.

Before activation:

- Confirm EMF extraction, expected metric dimensions and running-task coverage.
- Execute the actual Logs Insights queries and check time-series rendering.
- Capture staging evidence for idle, sustained saturation, recovery and missing
  or partial telemetry. An operator should be able to identify the affected
  service and any coverage gap without reading application code.
- Check collection overhead and agree operating thresholds and running costs.

Mock tests cannot replace these deployed checks or screenshots.

## Local and CI checks

The `terraform-test` CI job runs module-local mock tests without AWS credentials
or applying resources. Assertions cover order, placement/non-overlap, periods,
units, gauge statistics, deduplication and missing-data handling.

```sh
terraform -chdir=terraform/modules/puma_capacity_dashboard init -backend=false
terraform -chdir=terraform/modules/puma_capacity_dashboard validate
terraform -chdir=terraform/modules/puma_capacity_dashboard test
pre-commit run --config .pre-commit-config.yaml terraform_tflint --all-files
pre-commit run --config .pre-commit-config.yaml terraform_docs --all-files
```

Keep module source and mock assertions aligned with backend. Whoever changes
these files owns the paired update and checks in both repositories. The module
README is generated by `terraform-docs`; commit changes produced by that hook.
The application callers and CI Terraform versions remain repository-specific.
